# DeskMate Architectural Choices & Design Decisions

This document outlines the load-bearing engineering choices made during the development of the DeskMate IT Helpdesk AI Assistant.

---

## 1. Native Claude Tool Calling vs. ReAct/Intent Routing

During architectural evaluation, three distinct paradigms were considered: Pure ReAct string parsing, Static Intent Routing with deterministic loops, and Native LLM Tool Calling. DeskMate implements **Native LLM Tool Calling** for the following architectural reasons:

- **Constraint & Safety**: Predefined JSON schemas act as a strict interface contract. Unlike text-based ReAct loops (which rely on complex, error-prone regular expression matchers to parse text actions), native tool calling guarantees that inputs follow structured types. This makes the system resilient against prompt injections attempting to bypass Python validation.
- **Dynamic Multi-Step Reasoning**: Static intent routing requires the application code to forecast every possible workflow branch beforehand. If a user asks "Check my entitlement for Slack, and if I have it check my entitlement for Jira, and if not create a ticket for both," a static router fails. Claude's tool-use loop dynamically reasons through execution traces, executing multiple actions sequentially in a single user turn.
- **Token Efficiency**: Unlike text-based ReAct prompts which require massive system instruction blocks demonstrating the reasoning style, native tool calling is implemented at the model infrastructure level. This reduces prompt sizes, leading to lower request latency and token expenses.

---

## 2. Database Selection: MongoDB Atlas

MongoDB Atlas was chosen as the database provider for this proof of concept due to its direct alignment with modern IT infrastructure patterns:

- **Flexible Document Model**: IT tickets and employee entitlements are highly dynamic. MongoDB permits storing nested fields (such as changing maps of software keys in `entitlements`) without schema migrations.
- **Live Distributed Operations**: Using a live Atlas cluster simulates cloud connectivity, testing the system's ability to recover from real-world latency spikes, connection timeouts, and authentication drops.
- **JSON Compatibility**: MongoDB documents map directly to python dicts and JSON payloads, easing serialization throughout the agent loop and frontend observability console.

---

## 3. Web Framework: FastAPI vs. Streamlit

FastAPI was selected as the backend server for DeskMate instead of Streamlit:

- **State Separation**: Streamlit reruns the entire Python script on every user interaction, making it difficult to maintain clean asynchronous state, handle long-running agent connections, or manage individual user session traces. FastAPI offers a clean stateless REST API architecture, dividing frontend display logic from backend calculations.
- **Production Integration**: FastAPI's endpoints can easily be mounted into enterprise API gateways, integrated with third-party service desks (like ServiceNow or Jira Service Desk), or scaled horizontally behind a load balancer.
- **Native JSON Validation**: Using Pydantic models at FastAPI's controller level guarantees that malformed requests are intercepted with HTTP 400 Bad Request responses before consuming expensive LLM tokens.

---

## 4. Cascading Failure Prevention & Error Isolation

To prevent database or external service failures from crashing the client:

- **Graceful Degradation**: Every database query in `mongo_client.py` and tool in `tools.py` is wrapped in safe `try-except` blocks. If MongoDB Atlas experiences a connection drop or queries time out:
  1. The database driver returns an error dictionary (`{"error": "Database selection timeout"}`) rather than raising a runtime exception.
  2. The tool formats this cleanly for the LLM.
  3. Claude receives the error context as a `tool_result` and responds politely (e.g. *"I am experiencing temporary database connection issues. I am unable to verify your entitlement at this moment."*), ensuring user experience is preserved.
- **Agent Loop Capping**: To prevent infinite LLM loops (where tool errors cause Claude to endlessly retry calling the same tool), the runner loop in `agent.py` is hard-capped at **10 iterations**. If the agent exceeds this cap, the runner breaks and returns a graceful failure response.

---

## 5. Observability: End-to-End Tracing

Observability is a core requirement of DeskMate. Each user interaction returns an `execution_trace` containing:

- **Reasoning Process**: The exact API call duration, tokens consumed, and thoughts generated by the model.
- **Tool Executions**: Exact parameters, tool names, outputs, and database query latency.
- **Audit Trails**: Clear records of when tickets were modified or entitlements checked.

This execution trace is transmitted back as structured JSON, rendering live on the frontend observability panel to provide complete visibility into how the AI arrived at its conclusion.
